# Cucumber & BDD Best Practices

This skill provides actionable design principles, patterns, and runbooks for designing maintainable, business-readable Behavior-Driven Development (BDD) specifications and Cucumber automation frameworks.

---

## 🧭 Core Principles: The BDD Lifecycle

BDD is a collaborative methodology that aligns business stakeholders, developers, and QA engineers before code is written.

1. **Discovery (Shift-Left Collaboration)**:
   - Involve the "Three Amigos" (Product Owner/BA, Developer, QA) in Discovery workshops.
   - Use concrete examples to explore scope, uncover edge cases, and define boundaries.
   - See [Three Amigos & Discovery Guide](./references/three_amigos_and_discovery.md).

2. **Formulation (Living Documentation)**:
   - Formulate agreed examples into Gherkin specifications using business domain terms (Ubiquitous Language).
   - Ensure feature files remain the single source of truth for both humans and computers.

3. **Automation (Executable Specifications)**:
   - Connect Gherkin steps to code via thin step definitions.
   - Run automated scenarios as continuous regression guardrails.

## ✍️ Feature File & Scenario Authoring Rules

### Rule 1: Declarative over Imperative (Golden Rule)
- **Declarative (Required)**: Express user intent and business outcomes (`When I sign in with valid credentials`).
- **Imperative (Prohibited)**: Specifying clicks, keystrokes, field selectors, and UI mechanics (`When I type "user" in "#txt-box"`).
- Review [Declarative vs Imperative Examples](./examples/declarative_vs_imperative.feature).

### Rule 2: Single Responsibility & Scenario Length
- One business rule or behavior per scenario.
- Target **3 to 8 steps** per scenario.
- Avoid multi-stage workflows or long chains of `And` / `But` steps.

### Rule 3: Independence & Zero Interdependency
- Scenarios must be completely self-contained and order-independent.
- Never rely on state, cookies, or data generated by a previous scenario.
- Scenarios must be capable of running concurrently and in any arbitrary sequence.

### Rule 4: File Sizing & Domain Cohesion
- Target **5 to 10 scenarios per feature file**.
- Keep feature files domain-specific (e.g., `checkout.feature`, `user_login.feature`, `posts_api.feature`). Split oversized feature files into sub-modules.

## 🗂️ Background, Scenario Outlines & Data Tables

### When to Use `Background:`
- Use `Background` strictly when **every single scenario** in the feature file shares the exact same prerequisite setup steps.
- Keep `Background` minimal (1–3 steps max). Do not use `Background` to set up state needed by only a subset of scenarios.

### `Scenario Outline` vs. `Data Tables`
- **Use `Scenario Outline` with `Examples:`** when you need to execute the **same scenario workflow with different datasets** (data-driven testing).
- **Use `Data Tables`** when injecting **complex multi-attribute parameters into a single step** (e.g., creating a user profile or submitting a batch form).
- Review [Outlines & Data Tables Examples](./examples/scenario_outline_and_datatable.feature).

## 🏗️ Step Definition & Automation Architecture

### 1. Step Definitions are Pure Translation Layers
- Never embed raw locator lookups, database queries, or complex HTTP assertions directly in step definition methods.
- Delegate actions to:
  - **Page Object Models (POM)** or driver managers (e.g., `PlaywrightManager.getPage()`).
  - **API Service Clients** with request specifications and filters (e.g., `AllureRestAssured`).
  - **Assertions libraries** (Hamcrest, AssertJ).

### 2. Maximize Parameterization & Reusability
- Parameterize steps with Cucumber Expressions (`{string}`, `{int}`, `{word}`) to avoid duplicated glue code.
- Write generic assertion steps reusable across features:
  - `Then the response status code should be {int}`
  - `Then the page title should contain {string}`

### 3. State & Resource Cleanup
- Use tagged hooks (`@Before("@ui")`, `@After("@ui")`) for browser lifecycle and screenshot attachments on failure.
- Use ThreadLocal storage for browser, driver, and context instances to enable parallel test execution.

## 🏷️ Tagging Taxonomy & Execution Strategy

Categorize scenarios using structured tags:

- **Layer**: `@ui`, `@api`, `@db`
- **Scope**: `@smoke` (fast pipeline smoke test), `@regression` (comprehensive regression), `@wip` (work in progress)
- **Domain**: `@auth`, `@billing`, `@checkout`

### Execution Cheatsheet:
```bash
# Run smoke tests only
.\mvnw.cmd test -Dtest=CucumberTestRunner "-Dcucumber.filter.tags=@smoke"

# Run all API regression tests
.\mvnw.cmd test -Dtest=CucumberTestRunner "-Dcucumber.filter.tags=@api and @regression"

# Exclude work-in-progress scenarios
.\mvnw.cmd test -Dtest=CucumberTestRunner "-Dcucumber.filter.tags=not @wip"
```
